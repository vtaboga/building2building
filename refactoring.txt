Building2Building Refactoring Plan + Codex Execution Prompt
============================================================

Purpose
-------
This document prepares a major repository refactor focused on:
- Simpler architecture
- Pip-install-first usability
- Clear importable API for environments, training, and benchmarks
- Reduced Hydra leakage into core library code

IMPORTANT
---------
- Backward compatibility is NOT required.
- Prefer deleting obsolete code over carrying compatibility shims.
- Keep the resulting system simpler even if it means breaking old imports/configs.


1) Current pain points (observed)
---------------------------------
1. Core library and Hydra/CLI concerns are mixed:
   - Many core functions accept DictConfig/OmegaConf-like objects directly.
2. Public API is unclear:
   - Users must discover internals (`b2b.make_env`, `b2b.sources.*`, scripts).
3. Environment construction logic is duplicated in multiple places.
4. Dataset access naming is inconsistent:
   - `hydroquebec`, `single_zone_houses`, helper functions scattered in `utils.py`.
5. Benchmarks and training are script-centric, not library-centric.
6. Tests are not clearly layered (unit vs integration vs e2e).


2) Refactoring goals
--------------------
A. Create a clean, typed, importable library API:
   - Easy for external users after `pip install building2building`.
B. Make Hydra a thin CLI adapter layer only.
C. Centralize environment creation and dataset selection.
D. Keep task/reward/run-period/actuator-access as first-class, explicit concepts.
E. Provide simple benchmark interfaces for:
   - same-type train/test split
   - multi-type train/test split
F. Make tests and scripts predictable and maintainable.


3) Target architecture (proposed)
---------------------------------
Create the following package structure (or closest practical equivalent):

`b2b/api/`
  - Public, stable user-facing API
  - minimal imports:
    - `make_env(...)`
    - `make_single_zone_env(...)`
    - `make_multizones_env(...)`
    - benchmark builders/runners
    - training entrypoints

`b2b/config/`
  - Typed dataclasses/pydantic-like models for:
    - dataset selection
    - task config (run period, target mode, zone targets)
    - reward config
    - actuator access config
    - train/eval benchmark config
  - Parsing/validation helpers from dict

`b2b/envs/`
  - Environment factory and composition only
  - wrappers and simulator assembly
  - no Hydra-specific code

`b2b/datasets/`
  - Move/rename from `sources/` if feasible
  - one unified selection interface:
    - sample by split
    - select by split indices
    - select via metadata query
  - dataset-specific modules:
    - `single_zone_houses`
    - `multizones_reference_buildings`

`b2b/tasks/`
  - Task and reward composition logic
  - occupancy target logic, run periods, reward assembly

`b2b/benchmarks/`
  - Library benchmark interfaces and execution loops
  - no direct Hydra assumptions

`b2b/training/`
  - SB3-related training orchestration for library users

`b2b/cli/` (optional)
  - optional internal CLI adapters called by scripts

`scripts/`
  - thin wrappers only:
    - parse Hydra cfg
    - map to typed config objects
    - call API


4) Functional requirements to preserve
--------------------------------------
1. Run periods:
   - full_year, winter, summer
2. Reward support:
   - deadband, barrier + energy penalty
3. Target temperature modes:
   - constant
   - occupancy-dependent
   - zone-level overrides
4. Observation support:
   - occupancy and target temperatures included and normalized by wrappers
5. Building selection capabilities:
   - random sampling in split
   - split index selection
   - metadata search-based selection
6. Benchmark interfaces:
   - single-type train/test split
   - multi-type train/test split
7. OfficeMedium actuator-shift benchmark:
   - train without zone heating setpoint actuators, test with them
   - and vice versa through config
8. Discovery metadata extraction keeps short dummy run period default.


5) Non-goals
------------
- Backward compatibility with old module paths/config keys.
- Preserving old script behavior exactly if it conflicts with simplification.


6) Concrete migration tasks
---------------------------
Task 1: Establish typed config layer
  - Create canonical config models in `b2b/config/models.py`:
    - Dataset enum/name and selectors
    - TaskConfig
    - RewardConfig variants
    - ActuatorAccessConfig
    - EnvBuildConfig
    - Benchmark config models
  - Add strict validation and sane defaults.

Task 2: Consolidate dataset access
  - Introduce one unified interface module:
    - e.g., `b2b/datasets/access.py`
  - Move/merge functionality currently split across:
    - `b2b/sources/building_access.py`
    - `b2b/sources/single_zone_houses.py`
    - `b2b/sources/multizones_reference_buildings.py`
    - `b2b/utils.py` helpers
  - Remove duplicated split/index mapping logic.

Task 3: Simplify env factory
  - Replace mixed config parsing in `b2b/make_env.py` with typed config input.
  - Keep one canonical environment build path.
  - Dataset-specific selector logic should happen before env creation.

Task 4: Move task/reward assembly to dedicated module
  - Ensure reward + task behavior is composed in one place.
  - Keep simulator creation lean (wiring only).

Task 5: Rebuild benchmark interfaces cleanly
  - Keep/refine:
    - single-type split benchmark
    - multi-type split benchmark
  - Ensure train/test can use different task and reward configs.
  - Keep actuator-access toggles explicit.

Task 6: Refactor scripts into thin adapters
  - Scripts should:
    1) parse Hydra config
    2) map to typed model
    3) call API
  - No business logic in scripts.

Task 7: Clean package exports
  - Update `b2b/__init__.py` and `b2b/benchmark/__init__.py` exports.
  - Expose obvious import paths for users.

Task 8: Testing cleanup
  - Keep existing behavior tests where useful.
  - Add/update tests for typed parsing and unified dataset selection.
  - Ensure benchmark interface tests still pass.

Task 9: Documentation update
  - Update README to reflect new module paths and usage.
  - Add “library usage first” examples:
    - create env
    - train
    - run benchmark


7) Definition of done
---------------------
1. A user can pip install package and do:
   - `from b2b.api import make_env` (or equivalent clean API)
   - build single-zone and multizones envs with typed config
2. Scripts are thin and readable.
3. No OmegaConf/Hydra types in core library internals.
4. Benchmark APIs support both split scenarios and task shift.
5. Tests pass and README matches actual usage.


8) Recommended implementation order
-----------------------------------
1) typed config models
2) unified dataset access module
3) canonical env builder
4) benchmark API adaptation
5) script adapters
6) delete obsolete modules/functions
7) tests and docs finalization
